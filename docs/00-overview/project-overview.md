# 프로젝트 개요

## 1. 배경

국내 금융 앱(은행, 카드, 핀테크)은 **평소에는 트래픽이 일정**하지만, 출석체크·퀴즈·선착순 포인트 지급 같은 **마케팅 이벤트 시간대에는 접속이 수십~수백 배 폭증**한다.
이 상황에서 흔히 보이는 실패 패턴은 두 가지다.

1. **전체 MSA 전환** — 모든 도메인을 쪼개 네트워크 홉, 운영 복잡도, 비용이 증가.
2. **전체 오버프로비저닝** — 연 수십 시간의 피크를 위해 365일 큰 인프라를 유지.

또한 포인트는 이용자의 금전적 가치이므로(선불전자지급수단에 해당할 수 있음) **장애 시 잔액·원장 데이터 유실이 허용되지 않는다.**

## 2. 프로젝트 목표

| # | 목표 | 측정 지표 |
|---|---|---|
| G1 | 폭주 도메인만 분리해 탄력적으로 처리 | 이벤트 피크 시 p95 응답 < 500ms, 에러율 < 0.1% |
| G2 | 평시 비용 최소화 | 이벤트 외 시간 MSA 노드 0~1대 유지 |
| G3 | 리전 장애 시 핵심 기능 생존 | RTO ≤ 30분, RPO ≤ 5초 |
| G4 | 전 과정 코드화 | 인프라 100% Terraform, 배포 100% GitOps |
| G5 | 의사결정 근거 문서화 | 주요 선택마다 ADR 작성 |

## 3. 비즈니스 시나리오 (시나리오 B — 금융권)

| 도메인 | 기능 | 트래픽 특성 | 배치 |
|---|---|---|---|
| user | 회원가입, 로그인, 인증 | 일정 | Monolith |
| asset | 마이데이터 기반 자산 조회 (Mock 연동) | 일정, 출근시간 소폭 증가 | Monolith |
| point | 포인트 원장, 충전/사용/환불, 잔액 조회 | 일정 (이벤트 결과는 비동기 반영) | Monolith |
| cs | 고객센터 게시판, 공지 | 낮음 | Monolith |
| **event** | **출석체크, 퀴즈, 선착순 포인트 지급, 대기열** | **주 1~2회, 수백 배 폭주** | **MSA** |

### 대표 시나리오
> "매주 수요일 10:00, 선착순 10만 명에게 퀴즈 정답 시 500P 지급"
> → 09:55 KEDA Cron이 event-service를 사전 확장 → 10:00 트래픽 폭주 → Redis 대기열/중복 방지 → Kafka로 지급 이벤트 발행 → Monolith point 모듈이 멱등하게 원장 반영.

## 4. 범위

### In Scope
- AWS Main 환경 전체 (VPC, EKS, Aurora, ElastiCache, MSK, Route 53 등)
- GCP DR Pilot Light (Cloud SQL 상시 복제 + GKE 온디맨드 생성)
- Terraform 모듈, GitHub Actions CI/CD, ArgoCD GitOps
- 관측성(Prometheus/Grafana, CloudWatch), 부하 테스트(k6), DR 훈련
- 최소 기능의 애플리케이션 (인프라 검증 목적)

### Out of Scope
- 실제 마이데이터 API 연동 (Mock 서버로 대체)
- 실제 결제/PG 연동
- 프론트엔드 고도화 (간단한 웹 페이지 수준)
- 멀티 리전 Active-Active

## 5. 차별점 (포트폴리오 관점)

1. **"모든 걸 MSA로" 하지 않은 이유를 설명할 수 있다** — 비용·지연·운영 복잡도 기반 판단.
2. **DR을 "다 복제"가 아닌 "비즈니스 생존" 기준으로 설계** — 선택적 복구(이벤트는 닫음).
3. **RTO/RPO를 주장이 아닌 실측으로 증명** — DR 훈련 기록, CDC Lag 대시보드.
4. **FinOps 수치화** — Active-Active / Warm Standby / Pilot Light 비용 비교표.
