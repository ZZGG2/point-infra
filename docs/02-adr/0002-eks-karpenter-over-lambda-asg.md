# ADR-0002: 이벤트 확장에 EKS + Karpenter 채택
- 상태: Accepted · 날짜: 2026-11-05

## 맥락
이벤트 시작 순간(예: 10:00:00) 트래픽이 수 초 안에 수백 배로 뛴다. 평시에는 거의 0이다. 확장 속도, 평시 비용, DR 이식성을 동시에 만족해야 한다.

## 결정
event-service는 **EKS 위 컨테이너**로 운영하고, 파드는 **HPA + KEDA(Cron 사전 확장)**, 노드는 **Karpenter(Spot 우선)** 로 확장한다.

## 고려한 대안
| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| AWS Lambda | 진짜 Scale-to-zero, 관리 부담 없음 | 콜드 스타트(특히 JVM), 동시성 한도 사전 증설 필요, Redis/Kafka 연결 관리 어려움, **GCP로 이관 불가** | DR 이식성과 일관된 지연 보장 실패 |
| EC2 Auto Scaling Group | 익숙함 | 인스턴스 부팅 + 앱 기동에 수 분, 스케일 판단 주기가 김 | 선착순 피크(수 초)에 늦음 |
| ECS Fargate | 노드 관리 없음 | 태스크 기동 수십 초~, GCP 이식 시 재작성 | DR 이식성 |
| EKS + Cluster Autoscaler | 표준 | ASG 기반이라 노드 확장 느림, 인스턴스 타입 고정 | Karpenter가 우월 |
| **EKS + Karpenter + KEDA** | 노드 직접 프로비저닝(빠름), Spot 다양화, 사전 스케일, K8s 표준 → GKE 이식 | 컨트롤 플레인 고정비, 학습 곡선 | **채택** |

## 핵심 논리
- **"예측 가능한 피크"는 반응형이 아니라 예약형으로 막는다.** 이벤트 시간을 알고 있으므로 KEDA Cron으로 5분 전 확장 → 콜드 스타트 문제 자체를 제거.
- 반응형(HPA)은 예상을 넘는 트래픽에 대한 2차 방어선.
- 평시: event 네임스페이스 최소 레플리카 1(또는 0), Karpenter가 빈 노드 회수(consolidation).

## 결과
- (+) 이벤트 외 시간 MSA 노드 비용 ≒ 0
- (−) EKS 컨트롤 플레인 비용(시간당 $0.10)은 고정 → 모놀리스도 같은 클러스터에 올려 상쇄
- 후속: 부하 테스트로 "이벤트 시작 → 목표 처리량 도달 시간" 실측
