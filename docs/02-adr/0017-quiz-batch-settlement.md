# ADR-0017: 퀴즈 이벤트 보상을 이벤트 종료 후 일괄 정산
- 상태: Accepted · 날짜: 2026-11-17 · 용어 갱신: 본문의 "monolith" 는 core-service 로 읽는다 (#35)
- 관련: ADR-0004 (선택적 복구), ADR-0005 (CDC 비동기 복제), ADR-0007 (Redis 판정), ADR-0008 (Kafka 비동기 원장 반영)

## 맥락
- 퀴즈 당첨은 `Redis 판정 → Kafka(point.reward.requested) → monolith consumer → 원장` 순서로 **건별** 반영됐다.
- 피크 중 재해가 나면 당첨 건이 세 곳으로 흩어진다: Cloud SQL 까지 복제된 건 / RDS 에만 있는 건(≤ CDC Lag) / **MSK 에만 있는 건(consumer lag)**. MSK 와 Redis 당첨 기록은 DR 대상이 아니라(ADR-0004) AWS 와 함께 접근할 수 없다.
- 그 결과 DR 측에서는 **같은 이벤트의 당첨자 중 일부만 지급된 상태**가 되고, 어디까지 지급됐는지 판단할 기준도 없다. "전원 지급"도 "전원 미지급(취소 후 재진행)"도 기계적으로 결정할 수 없다.
- 스냅샷/PITR 로 되돌리면 이벤트와 무관한 결제·출석 거래까지 되돌아가므로 쓸 수 없다.

## 결정
퀴즈 이벤트(`reason=QUIZ_REWARD`)는 **즉시 지급하지 않고 이벤트 종료 후 한 트랜잭션으로 일괄 정산**한다. 출석체크는 기존대로 즉시 지급한다.

1. **이벤트 중**: consumer 는 당첨 메시지를 `point.reward_pending` 에 INSERT 만 한다 (원장·지갑 미변경, 행 잠금 없음, 멱등키 PK).
2. **이벤트 종료 후**: 정산 Job 이 `POST /api/admin/events/{eventId}/settlement {"expectedCount": Redis 당첨자 수}` 호출
   - 대기 건수 ≠ 당첨자 수 → 409 `SETTLEMENT_NOT_READY` (Kafka 반영 중, 원장 미변경) → 재시도
   - 같으면 **한 트랜잭션**: 지갑 잠금(user_id 순) → 대기 건 전부 원장 INSERT → 지갑 반영 → `point.event_settlement` 기록
3. **DR 판정**: `reward_pending`, `event_settlement`, 원장·지갑 모두 CDC 복제 대상. Cloud SQL 에서 정산 기록(`row_count`)과 원장 건수를 비교한다.

| Cloud SQL 상태 | 의미 | 조치 |
|---|---|---|
| 정산 기록 없음 | 정산 전 재해 → 원장에 이 이벤트 지급 0건 (**전원 미지급**) | DR 중 정산하지 않음. Failback 후 정상 정산, AWS 영구 소실이면 재진행/일괄 보상 (비즈니스 결정) |
| 정산 기록 있음, 원장 = row_count | 완전 반영 | 없음 |
| 정산 기록 있음, 원장 < row_count | 정산은 끝났는데 복제 도중 끊김 | 승격 Job 이 `settle-incomplete-events.sql` 로 대기 건에서 누락분 지급 (멱등). 대기 건도 모자라면 Failback 시 RDS 기준으로 완성 |

어느 경우든 **"일부만 받은 상태"가 판정 불가능한 채로 남지 않는다.**

## 고려한 대안
| 대안 | 장점 | 단점 | 기각 이유 |
|---|---|---|---|
| 건별 즉시 지급 (현행) | 당첨 직후 잔액 반영 | 재해 시 부분 지급 + 판정 기준 없음 | 이 ADR 의 문제 자체 |
| 클라우드 간 동기 2PC | 손실 0 | 모든 커밋에 클라우드 간 RTT, GCP 장애가 AWS 장애로 전파 | ADR-0005 와 같은 이유로 기각 |
| MSK → Cloud SQL inbox 별도 Sink | 즉시 지급 유지, DR 에서 미반영분 복구 | 메시지 스키마(Schema Registry) 도입, Sink lag 만큼은 여전히 유실 | 비용 대비 효과 낮음. 즉시 지급이 필수가 되면 재검토 |
| 재해 시 이벤트 전체 취소 (보상 거래) | 추가 인프라 없음 | 이미 쓴 포인트 회수 문제, Failback 때 MSK 잔여 메시지 재지급 차단 장치 필요, 미반영 당첨자 명단 부재 | 정산 방식이면 애초에 부분 지급이 생기지 않음 |
| PITR / 스냅샷 롤백 | 단순 | 이벤트 외 거래까지 롤백 | 불가 |

## 결과
- (+) 원본(RDS)에서 이벤트 단위 원자성: 전부 지급 / 전혀 지급 안 됨
- (+) DR 측에서 쿼리 한 번으로 완료 여부 판정, 재정산은 멱등이라 몇 번 돌려도 안전
- (+) 피크 중 consumer 는 INSERT 만 → 원장 행 잠금 경합 제거, lag 감소
- (−) 당첨 포인트가 이벤트 종료 후 지급 (프론트 문구: "이벤트가 끝나면 한 번에 지급돼요")
- (−) 정산 트랜잭션 크기 = 당첨자 수. 수십만 명 규모가 되면 청크 정산 + 정산 상태 테이블로 바꿔야 한다
- (−) 관리자 API 는 임시로 `X-Admin-Token`(ADMIN_API_TOKEN) 보호 → 관리자 역할(JWT role) 도입 시 교체
- 후속: 정산 Job(K8s CronJob/이벤트 종료 훅) 자동화, 이벤트 메타데이터(종료 시각) 저장소 도입 시 expectedCount 자동 조회
