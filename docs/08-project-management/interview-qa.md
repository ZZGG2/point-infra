# 예상 면접 질문 & 답변 논리

## 아키텍처

**Q1. 왜 전부 MSA로 하지 않았나요?**
> 트래픽 패턴이 다른 도메인은 이벤트 하나였습니다. 전부 쪼개면 서비스 간 네트워크 홉과 분산 트랜잭션이 생기고, 특히 포인트 원장은 강한 정합성이 필요해 Saga 같은 보상 로직이 필요해집니다. 그래서 확장이 필요한 이벤트만 분리하고 나머지는 모듈 경계를 지킨 모놀리스로 두었습니다. 경계는 ArchUnit으로 강제해서 나중에 분리 비용도 낮췄습니다. (ADR-0001)

**Q2. Lambda를 쓰면 Scale-to-zero가 더 쉽지 않나요?**
> 맞습니다. 다만 세 가지 이유로 배제했습니다. ① JVM 콜드 스타트와 동시성 한도로 선착순 첫 수 초의 지연이 불안정하고, ② Redis·Kafka 커넥션 관리가 어렵고, ③ DR 대상인 GCP로 그대로 옮길 수 없습니다. 그리고 이벤트는 시간이 정해져 있어서, 반응형 확장보다 KEDA Cron으로 5분 전에 미리 확장하는 게 더 확실했습니다. (ADR-0002)

**Q3. EKS 컨트롤 플레인 비용은 Scale-to-zero가 아니지 않나요?**
> 네, 시간당 고정비가 있습니다. 그래서 모놀리스도 같은 클러스터에 올려 고정비를 공유했고, 이벤트용 노드만 0까지 줄어들게 했습니다. "컴퓨팅 노드 기준 Scale-to-zero"라고 정확히 표현합니다.

## DR

**Q4. RPO 0이라고 할 수 있나요?**
> 아닙니다. 비동기 CDC라서 RPO는 수 초입니다. heartbeat 테이블로 복제 Lag을 측정했고 p99 X초가 나왔습니다. 동기 복제를 하면 RPO 0이 가능하지만, 모든 커밋에 클라우드 간 왕복 지연이 붙고 DR 쪽이 죽으면 Main 쓰기까지 멈춥니다. 금융 서비스에서 가용성을 희생하는 건 더 큰 손실이라 판단했습니다. (ADR-0005)

**Q5. 왜 AWS 다른 리전이 아니라 GCP인가요?**
> 리전 장애만 보면 AWS 타 리전이 훨씬 쉽습니다. 하지만 IAM이나 글로벌 컨트롤 플레인 같은 사업자 수준 장애에는 같은 운명이 됩니다. 비용을 감수할 수 있는 수준에서 사업자 리스크까지 분산하려고 Pilot Light로 GCP를 택했습니다. 대신 State, 이미지, ArgoCD, 시크릿이 AWS에 의존하지 않도록 따로 설계했습니다. (ADR-0003, 0010)

**Q6. AWS가 죽었는데 DR 파이프라인은 어떻게 실행하나요?**
> GitHub-hosted runner에서 실행하고, GCP 인증은 Workload Identity Federation, Terraform state는 GCS, 이미지는 Artifact Registry에 CI 단계에서 미리 이중 푸시합니다. ArgoCD도 GKE에 새로 설치합니다. AWS 리소스에 하나라도 의존하면 DR이 동작하지 않기 때문에 의존성을 전수 점검했습니다.

**Q7. 자동 Failover는 왜 안 했나요?**
> DB Primary가 바뀌는 전환이라 오탐 시 양쪽에 쓰기가 생기는 Split-brain 위험이 있습니다. 감지는 자동, 전환은 승인 1회로 두고, 승인 이후는 전부 자동화했습니다. RTO 예산에 승인 시간 5분을 포함했습니다. (ADR-0011)

**Q8. DR 시 이벤트를 닫으면 고객 불만은요?**
> 이벤트는 연기·재공지로 보상이 가능하지만 로그인·잔액 조회·환불이 안 되면 금전 피해와 민원으로 이어집니다. DR의 목적을 비즈니스 생존으로 정의했고, 이벤트까지 띄우면 Redis·Kafka·대규모 노드가 추가로 필요해 RTO와 비용이 모두 커집니다. (ADR-0004)

**Q9. 복제가 있으니 백업은 필요 없나요?**
> 필요합니다. 잘못된 DELETE 같은 논리 오류는 CDC가 그대로 복제합니다. 논리 오류는 Aurora PITR로 대응합니다.

## 운영 / FinOps

**Q10. Pilot Light로 얼마나 절감했나요?**
> (실측 후 기입) Active-Active 시뮬레이션 대비 DR 월 비용 X% 수준입니다. DR 컴퓨팅이 0이고 Redis·Kafka가 DR에 필요 없는 게 주요 요인입니다.

**Q11. 선착순 정합성은 어떻게 보장했나요?**
> 판정은 Redis Lua 스크립트로 중복 체크와 재고 차감을 원자 처리하고, 원장 반영은 Kafka at-least-once + 멱등키 유니크 제약으로 중복 반영을 막았습니다. 종료 후 Redis 당첨자와 원장을 대사합니다. 부하 테스트에서 당첨 1,000명 / 참여 5만 명으로 초과 지급 0건을 확인했습니다.
